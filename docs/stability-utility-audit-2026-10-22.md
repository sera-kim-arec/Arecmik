# Arecmik 안정성·활용성 점검

- 기준: `849ada4`, 웹 `2026.10.22.9`.
- 방법: 소스 검토, 실제 앱 UI + 모의 Firebase, 추가 장애 재현, 모의 데이터 검색 측정.
- 실제 개인 기록이나 운영 Firebase 설정은 읽거나 바꾸지 않았다.

## 평가

개인 일정·할 일과 나의 기록을 함께 관리하는 활용성은 좋다. WORK/LIFE 구분, 프로젝트 맥락 유지, 원본을 복사하지 않는 연결, 검색과 즐겨찾기가 실제 사용 목적에 맞는다. 장기 보관의 신뢰도는 동시 편집 보호·실패 저장의 재전송·이전 버전 복원을 우선 보완해야 한다.

## 확인된 약점

| 우선순위 | 항목 | 근거와 영향 | 개선 방향 |
| --- | --- | --- | --- |
| 높음 | 같은 글의 동시 편집 충돌 | 로컬 자동저장이 대기 중일 때 서버에서 새 본문을 받도록 재현했다. 이후 로컬 본문이 저장되고 원격 변경 내용이 사라졌으며 화면에는 ‘서버에 저장됨’이 표시됐다. 원격 변경 내용은 로컬 복구에도 남지 않았다. | 편집 시작 버전과 서버 버전을 비교하고 충돌하면 양쪽 내용을 보관. 사용자가 선택하기 전 덮어쓰지 않기. |
| 높음 | 자동저장 실패 후 재전송 | 모의 쓰기 실패 후 연결을 복구하고 `online` 이벤트를 보냈다. 임시 내용과 복구 안내는 남지만 원본은 갱신되지 않았고 자동저장용 ‘다시 시도’ 버튼도 없었다. | 명시적인 다시 저장과 연결 회복 시 재시도. 재전송에도 충돌 검사를 적용. |
| 중간 | 백업의 이전 버전 복원 범위 | 현재 가져오기는 같은 ID의 기록을 건너뛰고 없는 기록만 추가한다. 삭제한 문서의 복구에는 도움이 되지만, 이미 덮어쓴 같은 ID의 본문을 예전 백업 내용으로 되돌리는 기능은 아니다. | 현재 글을 유지하면서 백업 버전을 별도 복구본으로 열기, 제한된 개수의 이전 버전 보관. |
| 중간 | 오래된 글의 날짜 | 글에 별도 날짜가 없으면 기록 목록이 수정일을 사용한다. 예전 글의 오타를 고쳐도 오늘 날짜로 이동할 수 있다. | 기록일과 수정일을 분리하고, 사용자가 지정한 기록일 유지. |
| 조건부 | 알림의 도착과 동기화 | PC 알림은 열린 탭의 타이머를 사용하며 절전 중 지연될 수 있다. 네이티브 위젯의 정기 동기화는 약 한 시간 간격이고 Android 정확한 알람 권한에 따라 예약 방식도 달라진다. | 기존 알림 안내와 위젯의 최종 동기화 표시를 유지하고, 실기에서 PC 작성 → 폰 수신 흐름 점검. |

첫 두 항목은 운영 계정을 사용하지 않은 장애 주입 재현이다. 실제 두 기기의 로그인·전송 과정을 검증한 결과는 아니며, 동일한 앱의 저장·스냅샷 처리 경로에서 확인한 동작이다. 임시 복구가 있다는 사실만으로 다른 기기의 변경 내용까지 보존되는 것은 아니다.

소스 근거: `index.html`의 `queueAutoSave`, `runAutoSave`, `subscribeUser`, `previewBackup`, `applyBackup`, `archiveEntries`; `reminders-ui.js`의 `tick`, 설정 안내; Android `SyncJob`과 `ReminderScheduler`.

## 활용성

### 잘 맞는 사용 흐름

- 일정 상세 → 해당 날짜·프로젝트를 이어받아 기록 작성 → 기록에서 후속 할 일 생성 → 프로젝트에서 같은 원본 확인.
- WORK는 업무·마감, LIFE는 일상·개인 준비를 나누고, 공간별로 통합 검색.
- 직접 쓴 기록을 기본 보관함에 모으고, 완료한 할 일을 모든 기록으로 자동 복사하지 않는 구성.
- 프로젝트 핵심 메모는 요약으로, 진행 기록은 날짜별 이력으로 유지.
- 검색·즐겨찾기로 다시 쓰는 정보를 찾고, 폴더·프로젝트를 정리해도 내부 기록을 보존하는 구조.

### 더 편해질 지점

- 일정이나 프로젝트에서 쓰면 맥락이 이어진다. 기록 탭에서 별도로 쓴 글은 프로젝트나 관련 항목을 직접 지정해야 연결된다. 작성한 곳의 날짜·프로젝트 기본값을 일관되게 유지하는 것이 도움이 된다.
- 기록이 쌓일수록 ‘언제 썼는지’와 ‘최근 고쳤는지’를 구분해야 찾기가 쉬워진다.
- 재전송과 복구는 사용자가 원인을 추측하지 않아도 한 번의 행동으로 끝낼 수 있어야 한다.

## 검증 결과

- 앞선 동일 기준 버전의 전체 회귀 검사: **259개 통과**.
- 이번 점검에서 연결 흐름 14개 + 저장·복구 10개를 다시 실행: **24개 통과**.
- 추가 장애 재현 2건: 동시 변경 덮어쓰기, 실패 후 재연결 미전송을 확인.
- 검색 규모 측정: 약 500자 본문을 가진 100 / 1,000 / 3,000개의 모의 글. 3,000개에서 검색 이벤트의 동기 처리 약 **13~31ms**. 이 환경의 짧은 글 검색에서는 뚜렷한 지연이 관찰되지 않았다.
- 검색 수치는 서버의 headless Chromium 측정이며 초기 다운로드·렌더링 전체 시간, 사진이 많은 장문, 실제 폰 성능을 뜻하지 않는다.

실제 Android 키보드·절전·런처, 운영 Firebase에서의 두 기기 동시 편집과 알림 도착, 운영 보안 규칙은 별도 실기 검증이 필요하다. 신규 대규모 UI 개편보다 충돌 보호 → 재전송 → 이전 버전 복구 순으로 신뢰도를 높이는 것이 현재 사용 목적에 가장 도움이 된다.
